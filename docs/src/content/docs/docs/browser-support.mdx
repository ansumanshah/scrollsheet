## Caveats

<Aside type="caution" title="Below the version floor">
  Safari 15.4–17.1 supports `<dialog>` but not CSS `linear()`, so the spring falls back to a plain
  ease-out at the same duration. `scrollend` falls back to a ~120ms debounced scroll-silence check
  where unsupported.
</Aside>

<Aside type="caution" title="Scroll-driven animation gaps">
  The backdrop dim and `--scrollsheet-progress` run as CSS scroll-driven animations
  (`animation-timeline: scroll()`), on engines that support them,
  feature-detected once and stamped `data-scrollsheet-sda` on the dialog. Where unavailable,
  the same values update every frame from `onTravel`'s own JavaScript write
  instead. Two pieces stay JS-driven on every engine regardless: a stacked sheet's parent-panel
  recede (a sibling top-layer `<dialog>`, not a descendant the track's timeline can reach) and
  `backgroundEffect` (its target sits outside the dialog entirely).
</Aside>

<Aside type="caution" title="Close-request routing">
  Where `dialog.closedBy` exists (Chrome/Edge 134+, Firefox 141+), a modal sheet sets `closedby`
  to `closerequest` when `escapeDismissible` is on, `none` when it's off, so Esc and the Android
  back gesture route through the platform's own close-request machinery, not scrollsheet's
  manual handling. Never `closedby="any"`: `.scrollsheet-dialog` always covers the full
  viewport, so there's no "outside the dialog" region for a native light-dismiss to detect; it
  would add no usable outside region to the existing backdrop-click handling. Engines without
  `closedBy` keep the manual Esc/backdrop dismissal unchanged.
  Non-modal sheets (`modal={false}`) get no platform close watcher for free, so a dismissible
  one creates its own via `CloseWatcher` (Chrome 126+, Firefox 149+, touch-primary devices only) so Android
  back closes it instead of navigating the page. On those devices Esc is also a platform close
  signal, and non-modal Esc is deliberately scoped to focus inside the sheet so a desktop
  watcher would steal the page's Esc. Real-device verification on that path is still pending.
</Aside>

## Without `<dialog>`

The [Can I Use dialog data](https://caniuse.com/dialog) reported 97.12% support on
2026-11-04. Counting unknown usage as unsupported gives a conservative 2.88% without
native dialog support. Unknown traffic is included in that estimate, not evidence of a known browser limitation.

<div className="table-scroll prop-table">

| Browsers without native dialog support | |
| --- | --- |
| You get | A fixed-position modal: backdrop, tap-to-close, Escape, focus moved into the panel on open and restored to the trigger on close, body scroll locked. Panel sizes to content up to 85% of the viewport, then scrolls internally |
| Gone | Detents, drag, the enter/exit animation, the top layer (panel portals to `<body>` with a max `z-index` instead of a guarantee), the native focus trap. `Sheet.Handle` renders nothing |
| Still works | Every `--scrollsheet-*` theming variable (`-bg`, `-fg`, `-radius`, `-shadow`, `-backdrop`, safe-area) resolves the same way. `isSupported()` reports which path a browser takes |

</div>

The fallback keeps the content available without reproducing the native dialog or gesture engine.

Want your own UI instead of the built-in fallback? Check `isSupported()`
client-side, after mount, so server and client agree on the first render:

```tsx
import { useEffect, useState } from 'react';
import { Sheet, isSupported } from 'scrollsheet';
import 'scrollsheet/styles.css';

const [supported, setSupported] = useState(false);
useEffect(() => setSupported(isSupported()), []);

if (!supported) return <LegacyModal open={open} onClose={onClose} />;
return <Sheet.Root open={open} onOpenChange={(next) => { if (!next) onClose(); }}>...</Sheet.Root>;
```
